Socket Programming Overview

The practicals require implementing TCP/IP clients and/or servers using sockets — the OS abstraction for a specific port on a specific host.

Socket = IP address + port number (e.g. 192.168.0.1:80). The OS allocates a temporary ephemeral port (49152–65535) for the client side of a connection.

Building a Client

A client initiates the connection. The server waits.

  1. Open a client socket: specify the server's IP address and port.
  2. Write/read to/from the socket as you would a file or stream. Follow the protocol's dialogue rules — order matters.
  3. Close the socket when done.
ProtocolNotes
TCPAll three steps are explicit: SYN (connect), communicate, FIN (close).
UDPAll happens in one: specify destination and send datagram. No connection.
// Java TCP client skeleton
Socket socket = new Socket("localhost", 8080);
BufferedReader in  = new BufferedReader(new InputStreamReader(socket.getInputStream()));
PrintWriter   out  = new PrintWriter(socket.getOutputStream(), true);

String serverGreeting = in.readLine();  // wait for server to speak first
out.println("EHLO client.example.com");
String response = in.readLine();
socket.close();

Building a Server

When writing an application that serves as a server in client-server architecture, the application must open a socket that waits for connections.

  1. Request a server socket from the OS, specifying the port to listen on.
  2. Wait (block) for a client to connect. When a connection occurs, the OS records the client's IP+port.
  3. Read from and write to the socket, following the protocol dialogue.
  4. Close the socket when done.
  5. Loop back to wait for the next client.
Improved approach: Spawn a child process/thread to handle each client, so the server can accept new connections immediately while serving existing clients.
// Java TCP server skeleton
ServerSocket serverSocket = new ServerSocket(8080);
while (true) {
    Socket client = serverSocket.accept();  // blocks until connection
    // Spawn thread to handle this client (improved approach):
    new Thread(() -> handleClient(client)).start();
}

void handleClient(Socket client) {
    BufferedReader in  = new BufferedReader(new InputStreamReader(client.getInputStream()));
    PrintWriter   out  = new PrintWriter(client.getOutputStream(), true);
    // ... protocol dialogue ...
    client.close();
}

Practical 2 — Telnet Appointment Server

Build a Telnet server (on a custom port) that manages appointments.

  • Server waits for TCP connection on a specified port.
  • When client connects (via the telnet program), server displays a prompt or menu.
  • Client sends text commands; server processes and responds.
  • Server must handle the Telnet protocol dialogue (CRLF line endings, etc.).

The specific service offered by the Telnet protocol is a virtual terminal.

To open a Telnet connection to a web server manually: telnet www.example.com 80

  • Use ServerSocket to listen; Socket to communicate.
  • Use BufferedReader/PrintWriter on the socket.
  • Line termination: Telnet uses \r\n (CRLF). Strip \r (CR, ASCII 13) when reading; append \r\n when writing.
  • Run server in WSL: java -cp . YourServer &
  • Test: telnet localhost <port> from WSL or Windows.
// Reading with CRLF
String line = in.readLine();         // readLine strips \n but not \r
line = line.replace("\r", "");       // strip the leftover \r (ASCII 13)

// Writing with CRLF
out.print("250 OK\r\n");
out.flush();

CR = ASCII 13 (\r), LF = ASCII 10 (\n). Both must be used for Telnet/HTTP line endings.

The ESC character = ASCII 27 in decimal. "Dumb" terminals and Telnet emulators use ANSI escape sequences for formatting.

SequenceEffect
ESC[2J i.e. \033[2JClear screen
ESC[HMove cursor to top-left
ESC[y;xHMove cursor to row y, column x
ESC[1mBold
ESC[0mReset formatting

Java example — to print "Hello" on line 5 at position 20:

screen.write(27);          // ESC character (ASCII 27)
screen.print("[20;5HHello");  // move to col 20, row 5, then print
Echo behaviour (exam tested):
When writing a server for a Telnet client, the server should normally echo every character received, because the client may not be able to echo typed characters locally.

Double echo trap: If you turn localecho ON in your Telnet client while your custom server is ALSO echoing, you will see every character twice. Be careful during testing.

Fix for invisible typing: If you can see output but cannot see what you TYPE, use set localecho in the Telnet client shell (accessed via the escape character ^] i.e. Ctrl+]).

Practical 3 — HTTP World Clock

Build an HTTP server that responds to GET requests and returns HTML pages showing world times.

  • Listen on a TCP port (e.g. 8080).
  • Accept a client connection (e.g. browser or curl).
  • Read the HTTP request: GET /path HTTP/1.1 + headers, terminated by blank line.
  • Parse the request-line to extract the path.
  • Generate an appropriate HTTP response with correct headers.
  • Send the response and close the connection.

A technically compliant web server must respond to at least GET and HEAD requests.

Virtual hosting: The primary reason for the Host: header is to enable the server to host more than one site on the same IP address.

  • Use ZonedDateTime or TimeZone to get current time in different zones.
  • Generate HTML table or list showing times in multiple cities.
  • The path in the GET request can select which region to display.
  • MIME type for HTML: text/html; charset=UTF-8
  • Content-Length: must be the byte length of the body — compute before sending.
// Get current time in a timezone
ZonedDateTime now = ZonedDateTime.now(ZoneId.of("Africa/Johannesburg"));
String time = now.format(DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss z"));

// HTTP POST encoding (exam detail)
// POST data sent as key=value pairs with spaces replaced by + and URL-encoding applied
// Testing
curl http://localhost:8080/
telnet www.example.com 80   // manual HTTP test (type GET / HTTP/1.0 then blank line)

Valid HTTP/1.0 request (method MUST be uppercase):

GET / HTTP/1.0\r\n
Host: www.up.ac.za\r\n
\r\n

HTTP response format:

HTTP/1.1 200 OK\r\n
Content-Type: text/html; charset=UTF-8\r\n
Content-Length: <byte-length-of-body>\r\n
Connection: close\r\n
\r\n
<html>...body...</html>
CR = ASCII 13, LF = ASCII 10. Each header line must end with \r\n. The blank line separating headers from body is also \r\n.

General Notes & WSL Tips

  • Read the RFC for the protocol you're implementing — it defines exactly what's valid.
  • Use telnet <host> <port> as a manual testing tool for any text-based protocol server.
  • Use Wireshark to compare your implementation's traffic with a standard client/server.
  • Pay attention to line endings: HTTP and Telnet use \r\n (CRLF), not just \n.

⚠ Exam Traps

Telnet escape character: Ctrl+] opens the Telnet client console. This is called the escape character. To exit: type quit.
localecho double-echo trap: If localecho is ON in the client AND your server is also echoing characters, you will see every character twice during testing.
GET method must be uppercase. GET / HTTP/1.0 is valid; get / HTTP/1.0 is not.
Blank line is required after HTTP headers (and after SMTP header section) — it separates the header section from the payload.
CGI mechanics: CGI writes to standard output to send to browser; reads an environment variable set by the server to receive input. These exact mechanics are frequently tested.
CR is ASCII 13, LF is ASCII 10. Both required for proper Telnet/HTTP line endings — not just LF alone.
A server MUST support GET and HEAD to be technically compliant. Other methods (POST, PUT, etc.) are optional.
