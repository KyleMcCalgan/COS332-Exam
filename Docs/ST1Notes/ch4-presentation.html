Extended ASCII Trap

Suppose computers A and B both use "extended ASCII" but have no character conversion mechanism. What challenges will they experience?
They will NOT misinterpret standard digits or the 26 Latin characters (identical across all extended sets).
They will NOT misinterpret standard punctuation marks.
They will NOT misinterpret HTML markup like &euml; (markup relies on standard ASCII characters).
The real challenge: they will misinterpret the actual extended characters (e.g. an ë might be rendered as α) because different extended ASCII sets map the upper 128 characters differently.

UTF-8 Encoding

Variable-length encoding of Unicode. Backwards-compatible with ASCII.

BytesBit PatternCharactersAvailable bits
10xxxxxxx0–127 (ASCII)7 bits = 128 chars
2110xxxxx 10xxxxxx5+6 = 11 bits
31110xxxx 10xxxxxx 10xxxxxx4+6+6 = 16 bits
411110xxx 10xxxxxx 10xxxxxx 10xxxxxx3+6+6+6 = 21 bits → 2²¹ characters

Trailing octets always start with 10. This allows self-synchronisation: skip bytes starting with 10 to find the start of any character.

Length from first octet (exam question): Suppose the first octet of a UTF-8 character is 193 in decimal. How long is the character? 193 = 11000001 in binary. Starts with 110 → the character is exactly 2 octets long.
Capacity calculation: How many Unicode characters can be represented in UTF-8 using exactly 4 bytes? Pattern: 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx. Available x bits: 3+6+6+6 = 21. Therefore: 2²¹ characters.
Tracing a hex sequence: Consider 46 33 EA A7 98 20. How many characters?
46 (01000110) → starts with 0 → 1 char
33 (00110011) → starts with 0 → 1 char
EA (11101010) → starts with 1110 → expects 2 trailing octets → A7 (10...) and 98 (10...) are valid trailers → 1 char
20 (00100000) → starts with 0 → 1 char
Total = 4 characters.
Self-synchronisation & errors: Consider sequence 46 A7 20. Why is this incorrect? A7 = 10100111 — a trailing octet that is not preceded by a valid multi-byte leading octet. UTF-8 is self-synchronising: it simply skips the broken trailing octet and resyncs. Corrected sequence: 46 20 → 2 characters.

Character Encoding Negotiation

Accept-Charset: iso-8859-1, utf-8, utf-16, *;q=0.1
  • Higher q value = higher preference (default q=1.0).
  • * is a wildcard matching any charset.
Wildcard trap: If the request is Accept-Charset: iso-8859-1, utf-8, utf-16, *;q=0.1 and the server supports iso-8859-1, utf-8, and Shift_JIS — the server may encode using any of these, including Shift_JIS. The * wildcard makes Shift_JIS acceptable even though it has low preference 0.1.

4.3 Grammar-Based Specification

  • BNF — Backus-Naur Form (developed for Algol by Backus and Naur).
  • ABNF — Augmented Backus-Naur Form. The HTTP protocol is specified using ABNF (not EBNF — a common exam trap).
  • EBNF — Extended BNF (different from ABNF; offered as a trap in exams).
Request-Line = Method SP Request-URI SP HTTP-Version CRLF
Method       = "OPTIONS" | "GET" | "HEAD" | "POST" | "PUT" | ...
CRLF         = CR LF

ASN.1 — Abstract Syntax Notation One

Formal notation for structured data (like a struct). Used in SNMP and X.509. Abstract — doesn't specify encoding. Encoding rules are separate:

Courses ::= SET {
  code       VisibleString,
  courseName VisibleString,

ASN.1 is more compact than XML but not human-readable without tools.

4.4 Non-Textual Data

The presentation layer identifies type, encoding, and structure:

  • Data type → category (text, image, audio)
  • Encoding → specific format (UTF-8, JPEG, MP3)
  • Markup → metadata (HTML tags, EXIF geo-tags — embedded metadata in photographs: shutter speed, GPS location)
  • Application-level format → domain-specific (SOAP envelope, XBRL)

4.5 MIME — Multipurpose Internet Mail Extensions

Originally for email; now widely used in HTTP. Solves sending non-ASCII data over 7-bit ASCII channels.

Valid MIME Top-Level Types (Highly Tested!)

VALID top-level MIME types: application, audio, example, image, message, model, multipart, text, video.
INVALID (exam traps): data, binary, text/text, vnd.
Note: model is often used as the correct answer because students forget it exists.

Common Content-Types

Multipart content uses a boundary parameter — a long, random string that marks the breaks between parts. It is critical that this string does not accidentally appear in the actual payload.

Content-Transfer-Encoding

Old protocols like SMTP were designed strictly for 7-bit ASCII lines. Binary data breaks them. MIME uses this header to safely encode data.

EncodingDescription
7bit / 8bit / binaryIdentity transformations — no change to the data; just declares the format to the lower layer.
base64Transforms 8-bit binary to safe 7-bit ASCII. Takes 3 bytes (24 bits) → 4 characters (6 bits each). Common for attachments. Use for PNG/JPEG via SMTP.
quoted-printableEncodes but keeps text human-readable. Normal ASCII stays as-is. Special chars encoded as =XX (hex). = itself becomes =3D. ABC could be =41=42=43.
Which encoding for a PNG via SMTP? Answer: base64.

Base64 Padding — The Rule of 3

Data is processed in groups of 3 bytes (24 bits) → 4 characters (6 bits each).

Remaining bytesActionPadding

1 byte left (8 bits)Add 4 zero bits → 12 bits → 2 characters==

Quoted-Printable — Soft Line Breaks

Used to ensure email systems don't break long lines of text:

  • Lines are restricted to 76 characters.
  • Soft break: An = is placed at the very end of a line (no visible content).
  • When the client sees the trailing =, it ignores the line break and joins the text back together.

4.6 Data Exchange Formats

Container formats: Wrap multiple content pieces + metadata (e.g. WMA wraps audio + DRM + codec info). Key question: does the container support streaming?

Serialisation: Converts data structures to linear sequences for storage/transfer.

Interchange formats: CSV, XML, LDIF (LDAP, RFC 2849), MBX (email mailboxes), JSON, ASN.1.

n² converter problem: With n formats, you need n² converters for all pairs. A universal format reduces this to 2n converters (each format only converts to/from universal).

4.7 Compression

LosslessExact original recoverableRLE, LZ, Huffman — required for text and financial data

Run-Length Encoding (RLE)

Replaces runs of repeated characters with count + character. Format: <ESC><count><char>

Example: 28 spaces → <ESC><28><space>

Bit-based RLE: encode as sequence of run lengths (alternating 0s and 1s). First bit assumed 0 (if not, first run length = 0).

Example: 000011100000111000000 → 4,3,5,3,6

Efficient only for long runs. Short runs can increase data size.

Lempel-Ziv Compression

Finds repeated phrases/byte sequences and replaces subsequent occurrences with pointers to earlier occurrences.

  • Format: <ESC><pointer><length>
  • Relative pointers (e.g. 16-bit = can reference up to 64KB back).
  • Minimum phrase length worth compressing = size of the pointer.
  • Variants: LZ77, LZ78, LZW (Welch). Basis for gzip, ZIP, PNG.

Huffman Codes

Variable-length codes where frequent characters get shorter codes and rare characters get longer codes.

  1. Treat each character as a leaf node with its frequency as weight.
  2. Repeatedly combine the two lowest-frequency trees into a new tree (parent = sum of children). Label branches 0 and 1.
  3. Repeat until one tree remains.
  4. Read code for each character by following path from root to leaf.

Example from notes (A=20%, B=10%, C=20%, D=15%, E=35%):

Step 1: Combine B(10%) + D(15%) → BD(25%)
Step 2: Combine A(20%) + C(20%) → AC(40%)
Step 3: Combine BD(25%) + E(35%) → BDE(60%)
Step 4: Combine AC(40%) + BDE(60%) → root(100%)

Result: A=00, B=100, C=01, D=101, E=11
(E = most frequent → shortest code 2 bits; B = least frequent → longest 3 bits)

⚠ Exam Traps

HTTP uses ABNF — NOT EBNF. EBNF is frequently given as a trap option. HTTP is specified using Augmented Backus-Naur Form (ABNF).
model is a valid MIME top-level type. Students forget it. Exam often uses it as the correct answer. Invalid types: data, binary, text/text, vnd.
Base64 encoding for PNG/images: Always use base64 when transferring binary data (images, files) via SMTP. Quoted-printable is for text content that needs to stay human-readable.
Extended ASCII trap: Standard ASCII chars (digits, 26 Latin letters, standard punctuation, HTML markup) remain correct between different extended ASCII sets. Only the actual extended characters (the upper 128) are misinterpreted.
UTF-8 length from first byte: 0=1 byte, 110=2 bytes, 1110=3 bytes, 11110=4 bytes. Trailing bytes always start with 10. Four-byte UTF-8 can represent 2²¹ characters (3+6+6+6 = 21 x bits).

Memo / Answer Key

MCQ Answers

A1. B (Layer 6 — presentation layer).
A2. A (ASCII — the one character set that HTTP assumes all parties understand).
A3. D (Any of the encodings — the *;q=0.1 wildcard covers Shift_JIS).
A4. A (binary is not a valid MIME top-level type).
A5. D (multipart/mixed — HTML + images = multiple different types).
A6. D (multipart/mixed — HTML message body + JPG attachment).
A7. C (n = 21; 4-byte pattern has 3+6+6+6 = 21 available bits).
A8. E (D7 E5 is not valid — D7 starts with 110 indicating a 2-byte char, but E5 starts with 1110, which is a 3-byte leading byte, not a valid trailing byte).
A9. D (base64 — converts binary to 7-bit ASCII safe for SMTP).
A10. E (It depends — all layers 3 to 7 are options).
A11. E (None of the listed problems will occur — standard text arrives fine — but other severe challenges do exist: extended characters above position 127 will be misinterpreted).
A12. C (ABNF — Augmented Backus-Naur Form).

Long-Form Answers

A13. UTF-8 encoding:

(i) U+00C6 (Æ):
U+00C6 = binary 0000 0000 1100 0110. Fits in 2-byte UTF-8 range (U+0080–U+07FF). Pattern: 110xxxxx 10xxxxxx.
Insert 11 bits 000 1100 0110: 110 00011 10 000110 → C3 86.

(ii) U+1040B:
Requires 4 bytes (> U+FFFF). Binary: 0001 0000 0100 0000 1011 = 21 bits.
Pattern: 11110xxx 10xxxxxx 10xxxxxx 10xxxxxx.
Bits: 000 010000 010000 001011 → 11110 000 10 010000 10 010000 10 001011 → F0 90 90 8B.

(b) 3-byte capacity:
Pattern 1110xxxx 10xxxxxx 10xxxxxx: 4+6+6 = 16 bits → n = 16 → 2¹⁶ = 65,536 characters.

A14. UTF-8 decoding:

(a) C3 86: C3 = leading 2-byte, data bits 00011. 86 = trailing, data bits 000110. Combined: 00011 000110 = 0x00C6 → U+00C6 (Æ).

(b) F0 90 AB 90: 4-byte sequence. Data bits: 000 010000 101011 010000 → combined = 0x10AB0 → U+10AB0.

(c) E2 B2 A0: 3-byte sequence. Data bits: 0010 110010 100000 → combined = 0x2CA0 → U+2CA0.

A15. Extended ASCII challenges:

  • (i) Z — no challenge. Z (ASCII 90) is in the lower 128 characters, identical in all ASCII variants.
  • (ii) ë — severe challenge. ë is in the upper 128. Computer B may map that byte to a completely different character if it uses a different extended ASCII variant.
  • (iii) &euml; — no challenge. The markup uses only standard ASCII characters (&, e, u, m, l, ;), all in the lower 128.
